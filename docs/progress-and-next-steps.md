## 3. 次に取り組む順番

**まずGoogleログインを設定し、公開版で「ログイン → 保存 → スマホで確認」を通してください。** 以下は作業のおすすめ順です。メール認証で先にログインできる場合は、Googleの設定を待たず手順2・3を進められます。

### 手順1：Googleログインを有効にする

1. [Google設定手順](google-public-login.md)を開き、Google CloudでOAuthクライアントを作成します。OAuthは、Googleのログイン結果を使ってこのアプリへ入る仕組みです。
2. 「ウェブアプリケーション」を選び、次の宛先を登録します。
3. Renderの環境変数へ `GOOGLE_CLIENT_ID` と `GOOGLE_CLIENT_SECRET` を設定し、再デプロイします。
4. [公開設定API](https://kotoba-qv50.onrender.com/api/config)で `google: true` を確認します。
5. 公開アプリの「Googleでログイン」から入り、ホームが表示されることを確認します。

| 設定 | 値 |
| --- | --- |
| JavaScript生成元 | `https://kotoba-qv50.onrender.com` |
| リダイレクトURI | `https://kotoba-qv50.onrender.com/api/auth/callback/google` |

リダイレクトURIは「Google認証後に戻る宛先」です。文字や末尾の `/` が違うと認証に失敗することがあります。確認元：[Google公式](https://developers.google.com/identity/protocols/oauth2/web-server)、[Better Auth公式](https://better-auth.com/docs/authentication/google)。

**完了条件：** 設定APIが `google: true` になり、実アカウントでログインできること。`true` への変更だけでは完了にしません。

同じメールアドレスで既存アカウントがある場合は、元のログイン方法で入り、「設定」の「Googleを連携」を使います。このアプリは同じメールアドレスだけを理由に自動統合しません。確認元：[アカウント画面](../src/components/auth/AccountPanel.tsx)、[認証設定](../server/backend.ts)。

### 手順2：公開版のPCで保存・学習を確認する

普段の教材と区別できる「動作確認用」単語帳を使います。

1. 公開URLへログインし、「動作確認用」の単語帳を作成します。
2. 「テクノロジ系」→「基礎理論」の順でフォルダーを作成します。
3. 「基礎理論」へ、問題「RFP」、答え「Request for Proposal」、補足「提案依頼書」を登録します。
4. ページを再読み込みし、フォルダーと単語が残ることを確認します。
5. カード式で答えを表示し、「覚えた」を押します。再読み込みして状態が残ることを確認します。
6. ログアウトして同じ方法で再ログインし、保存した内容を確認します。
7. 4択を使う場合は、異なる答えが4つ以上ある教材を用意して確認します。

**完了条件：** 単語本文・所属フォルダー・学習状態が再読み込みと再ログイン後も残ること。操作方法の確認元：[README](../README.md)。

### 手順3：スマホ実機で同期・操作を確認する

1. PCの「スマホで開く」からQRを表示し、スマホのカメラで読み取ります。
2. PCと同じ公開URL・同じアカウントでログインします。
3. PCで登録した「RFP」が表示されることを確認します。
4. スマホで補足を「スマホから更新」に変更し、保存します。
5. PCを再読み込みし、その変更が表示されることを確認します。
6. PCでも単語を追加し、スマホを再読み込みして反映を確認します。
7. スマホで入力欄、画面キーボード、スクロール、スワイプ学習を試します。
8. Wi-Fiを切って携帯回線でも公開URLへ接続します。端末とブラウザー名を記録します。

**完了条件：** PC→スマホとスマホ→PCの両方向で、保存後の再読み込みによる反映を確認できること。実際に使った端末のみを「確認済み」にします。

以前の記録はブラウザーによるタッチ再現と検証用環境の結果です。実機の確認元と混同しないでください：[スマホ公開資料](mobile-publishing.md)。既存検証記録はローカルの `.artifacts/mobile-browser-report.json` にあります（Git管理対象外）。

### 手順4：メール認証・パスワード再設定を確認する

1. 自分が受信できる確認用メールアドレスで新規登録します。
2. 確認メールが届くか、迷惑メールフォルダーも含めて確認します。
3. メールの確認リンクを開き、ログイン・保存ができることを確認します。
4. ログアウトし、「パスワードを忘れた方」から再設定します。
5. 新しいパスワードでログインでき、古いパスワードでは入れないことを確認します。
6. 別の確認用アカウントでもログインし、最初のアカウントの単語帳が表示されないことを確認します。

**完了条件：** 実メールでの確認・再設定・利用者ごとのデータ分離が成立すること。設定APIの `true` だけでは完了にしません。

送信方式の設定は[アカウント設定](account-setup.md)を参照してください。公開APIからは、SMTP・Resend・Brevoのどれが使われているかまでは判別できません。未確認の送信方式を前提に変更しないでください。

### 手順5：AI生成を実サービスで確認する

1. [AI生成の説明](ai-generation.md)に沿って、対象環境の `GEMINI_API_KEY` 設定を確認します。
2. ローカルの検査内容だけを見る場合は、次を実行します。

   ```powershell
   npm run ai:smoke -- --dry-run
   ```

3. ローカルの実Gemini接続を確認する場合は `npm run ai:smoke` を使います。このコマンドの成功と、公開版の成功は別です。
4. 公開版でも「資料からAIで生成」を開き、自作の短い文章から5語程度を生成します。
5. 問題・答え・補足を元の文章と照合し、候補を編集して登録します。
6. 再読み込みし、登録先のフォルダーに単語が残ることを確認します。

**完了条件：** 公開版から実サービスで生成し、内容を人が確認したうえで登録・再表示できること。生成候補の形式チェックだけでは、答えの正確さは確認できません。

### 手順6：バックアップと復元を確認する

**PCのSQLiteと、公開版のPostgreSQLでは手順が異なります。** 既存資料では公開版をRender + Supabase構成としていますが、今回の公開APIだけでDB提供元までは確認できません。管理画面で現在の構成を確認してから進めます。

| 保存先 | 実施すること |
| --- | --- |
| ローカルSQLite | `npm run backup` → `npm run backup:verify -- ".backups/作成されたフォルダー名"` → 別の検証環境に復元 |
| 公開版PostgreSQL | 現在の提供元の手順でDBをエクスポート → 元DBを上書きしない検証環境へ復元 → ログインと教材を確認 |

`npm run backup` はPostgreSQLのバックアップには対応せず、`DATABASE_URL` があると停止します。CSVは教材の移動用で、アカウント・フォルダー階層・学習状態を含む完全バックアップではありません。確認元：[バックアップ手順](backup-and-sharing.md)、[SQLite用スクリプト](../scripts/backup-sqlite.mjs)、[READMEのCSV説明](../README.md)。

Supabaseを使っている場合、無料プランでは定期的なデータのエクスポートと別の場所での保管が公式に推奨されています。確認元：[Supabase公式バックアップ資料](https://supabase.com/docs/guides/platform/backups)（2026年10月5日確認）。

**完了条件：** バックアップを作るだけでなく、検証環境でログイン・単語・フォルダー・学習状態を復元できること。認証用の `BETTER_AUTH_SECRET` もDBと別に保管します。

1. 手順1〜4・6の結果を記録します。AIを利用してもらう場合は手順5も完了させます。
2. 公開URL、ログイン方法、最初の単語帳の作り方を案内します。
3. 「登録できない」「保存されない」「スマホで押せない」など、基本操作の問題から修正します。

LINEログインは、LINEを使って試す人がいる場合に[設定手順](account-setup.md)に沿って追加します。ホーム画面への追加、オフライン利用、長期の学習グラフなどの追加検討は、公開版の基本動作を確認した後に進めます。

## 4. 普段の開発手順

PowerShellでプロジェクトのフォルダーを開きます。次のパスは、自分が配置した場所に読み替えてください。

```powershell
Set-Location -LiteralPath 'C:\作業用\kotoba-flashcards'
npm run dev
```

[ローカル画面](http://127.0.0.1:5173/)を開きます。画面とAPIが同時に起動します。依存関係がない場合や別のPCで始める場合は、先に `npm ci` を実行します。停止は `Ctrl + C` です。ローカルURLと公開URLの保存内容は、同じメールアドレスでも共通とは限りません。

コードを変更したら、次を確認します。

```powershell
npm test
npm run lint
npm run build
```

テストは処理の結果、Lintはコードの静的な問題、ビルドは型の確認と公開用ファイルの生成を確認します。その後、変更した画面を実際に操作します。確認元：[コマンド定義](../package.json)。

資料の変更だけなら、リンク先・操作名・実際の確認結果との一致を確認します。未確認項目を、日付を変えただけで確認済みにしないでください。

## 5. 問題が起きたときの確認先

| 症状 | 最初に確認すること |
| --- | --- |
| Googleボタンが「準備中」 | 公開設定APIの `google`。`false` なら環境変数と再デプロイを確認 |
| `redirect_uri_mismatch` | Google登録のURIと、アプリの本番URL・コールバック先が一致しているか |
| 確認メールが来ない | 迷惑メール、送信サービスの配信ログ、送信元の設定を確認 |
| 別端末の変更が見えない | 同じ公開URL・同じアカウントか、保存後に再読み込みしたか |
| 他端末の更新によって保存できない | 未保存入力を控えて再読み込み。古い内容をそのまま上書きしない |
| AI機能の準備案内が出る | 対象環境のAPIキー設定を確認。ローカルの設定だけで公開版も有効になったとは考えない |
| PostgreSQLで `npm run backup` が止まる | 対応するDBのエクスポート方法に切り替える |

エラーメッセージは実際に表示されたものを記録します。原因が特定できない場合は「未確認」、原因の見立ては「推測」と書きます。
